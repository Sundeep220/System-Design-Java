# Safepoints — Deep Dive

Safepoints are specific points in JVM bytecode execution where all running threads can be safely paused. They are the fundamental mechanism behind Stop-The-World GC pauses, deoptimization, thread dumps, and many other JVM operations.

> **A safepoint is a moment where the JVM can guarantee a consistent view of the heap — all object references are in known locations and can be traced. Without safepoints, GC and other JVM operations cannot safely examine the heap.**

---

# 1. What is a Safepoint?

During normal execution, a thread's registers may hold object references that the GC doesn't know about:

```text
Java thread executing:
  x = compute(a, b)

Inside compute:
  - Object `a` might be in a CPU register
  - Object `b` might be in a CPU register
  - The stack frame is changing

GC starts and wants to trace all objects...
Problem: where is `a`? It's in a CPU register — the GC doesn't know which register!
```

A safepoint is a point in execution where:

```text
1. No object references are in CPU registers
   (they've been stored back to known memory locations — stack frame or heap)

2. The thread's state is fully consistent
   (all operations are at a well-defined boundary)

3. The JVM knows exactly where all object references are
   (via pointer maps generated by the compiler)
```

At a safepoint, the JVM can safely:
- Examine all object references
- Move objects (copying GC)
- Update references to moved objects
- Inspect thread stack frames
- Take a thread dump

---

# 2. When Do Safepoints Occur?

The JVM compiler inserts safepoint checks at specific locations:

```text
Safepoint poll locations (inserted by JIT compiler):

1. Method calls (before/after)
2. Backward branches in loops (every loop iteration)
3. Return from methods

NOT inserted in:
  - JNI calls (native code doesn't have safepoint polls)
  - Very tight loops that the JIT analyzes specially
```

Bytecode with safepoint checks conceptually looks like:

```text
for (int i = 0; i < n; i++) {
    // Safepoint poll: check if JVM wants to pause
    if (safepoint_requested) {
        // reach safepoint: save state, signal JVM "I'm ready"
        wait_for_safepoint_end();
    }
    doWork(i);
}
```

In practice, the "check" is an optimized memory read — on most platforms, the JVM simply reads from a specific memory page that is normally readable but is write-protected when a safepoint is requested. The page fault triggers the safepoint.

---

# 3. Stop-The-World via Safepoints

When the JVM needs all threads stopped (for GC, thread dump, deoptimization):

```text
Step 1: JVM raises safepoint request flag
        (marks the polling page as inaccessible — causes SIGSEGV on access)

Step 2: All threads reach their next safepoint
        Threads in safepoint polls: stop at the poll
        Threads in blocking/waiting: already safe (not executing Java code)
        Threads in JNI: complete current JNI call, then stop before returning to Java

Step 3: All threads confirm they've stopped
        (each thread writes to a per-thread "I'm at safepoint" flag)

Step 4: JVM operation runs (GC, deoptimization, etc.)

Step 5: JVM releases safepoint flag

Step 6: All threads resume execution
```

---

# 4. Time to Safepoint (TTSP)

**Time to Safepoint** is how long it takes from the JVM requesting a safepoint until ALL threads have reached one. This is a hidden component of GC pause time:

```text
GC Pause = Time to Safepoint + Actual GC Work Time

Example:
  GC requested at T=0
  Thread 1 reaches safepoint at T=5ms
  Thread 2 reaches safepoint at T=8ms
  Thread 3 reaches safepoint at T=50ms  ← SLOW! Stuck in long loop?
  
  Actual GC starts at T=50ms (must wait for ALL threads)
  GC work takes 20ms
  GC pause = 70ms total  (50ms TTSP + 20ms GC work)
```

TTSP is the hidden problem: even if your GC work takes 10ms, if TTSP is 200ms, your effective pause is 210ms.

---

# 5. What Causes Long TTSP?

### 1. Thread Stuck in Long Loop Without Safepoint

The JIT may optimize a counted loop by removing safepoint polls:

```java
// JIT might decide: this loop is so tight, no safepoint poll needed
for (int i = 0; i < 1_000_000_000; i++) {
    sum += i;  // very tight, JIT-optimized
}
// Thread can run for seconds without reaching a safepoint!
```

During this loop, the thread never reaches a safepoint → GC must wait for it to finish.

Fix: `-XX:GuaranteedSafepointInterval=1000` (force a safepoint every N ms, deprecated in newer JVMs)

Or restructure the loop to have method calls or yield points.

### 2. Thread Executing Native Code

Threads in JNI don't have safepoint polls. They must complete the native call before reaching a safepoint.

A slow native call (blocking syscall, heavy computation) → long TTSP.

### 3. Inflated Lock Acquisition / OS Wait

A thread in a blocking OS wait is actually "safe" (not executing Java code) — these contribute much less to TTSP.

# 6. Safepoint Bias in Profiling

This is the safepoint bias problem mentioned in the CPU Profiling doc.

Sampling profilers that only sample at safepoints see a biased picture:

```text
Reality:
  Method A: 40% of CPU time (tight loop, few safepoints)
  Method B: 60% of CPU time (many method calls = many safepoints)

Safepoint-biased profiler sees:
  Method A: 10% (few safepoints → few samples taken in A)
  Method B: 90% (many safepoints → many samples taken in B)

WRONG! Profiler overestimates B, underestimates A.
```

Solution: `async-profiler` uses `AsyncGetCallTrace` (Linux perf signal) to sample at ANY point, not just safepoints → unbiased profiles.

# 7. Operations Requiring Safepoints

Many JVM operations require safepoints beyond GC:

```text
Garbage Collection           → most common reason
JIT Deoptimization           → when JIT optimizations must be undone
Thread Dump (jstack)         → takes snapshot of all thread stacks
Class Redefinition (jvmti)   → hot code replacement, debugging
Biased Lock Revocation       → when biased lock must be revoked
Deflate Monitors             → return inflated monitors to thin state
-XX:+PrintSafepointStatistics → logs every safepoint operation
```

# 8. Monitoring Safepoints

```bash
# Enable safepoint logging (Java 8)
-XX:+PrintSafepointStatistics
-XX:PrintSafepointStatisticsCount=1

# Java 9+
-Xlog:safepoint*:file=safepoints.log:time,uptime

# Sample output:
         vmop                    [threads: total initially_running wait_to_block]    [time: spin block sync cleanup vmop] page_trap_count
1.234: ParallelGCFailedAllocation [       15          1              1    ]      [   0     0    50    0   25  ]   1   1
        → time=50ms (spin waiting for thread to reach safepoint!)
```

Key fields:
- `spin`: time spent spinning waiting for threads to reach safepoint
- `sync`: time for all threads to sync (= TTSP)
- `vmop`: time of the actual JVM operation (GC work)

If `spin` or `sync` is much larger than `vmop` → safepoint latency problem.

---

# 9. Safepoints and Virtual Threads (Java 21+)

Java 21 virtual threads (lightweight threads) change the safepoint story:

```text
OS Thread (carrier thread):  1 carrier per CPU core
Virtual Threads:             thousands/millions of virtual threads

Safepoints for GC:
  Need to pause carrier threads (not virtual threads directly)
  Virtual threads at blocking operations (network wait) → auto-unmounted from carrier
  → Carrier thread can reach safepoint while virtual thread "waits"
  
Virtual threads dramatically reduce TTSP issues:
  Fewer carrier threads → faster safepoint convergence
  I/O-bound virtual threads don't block carrier threads
```

This is one reason virtual threads are better for high-concurrency I/O-bound workloads.

# 10. Summary

```text
Safepoint:
  A consistent point in thread execution where the JVM can safely:
  - Examine/move objects (GC)
  - Take thread dumps
  - Deoptimize JIT-compiled code
  - Apply class redefinitions

When they occur:
  - Method calls
  - Backward loop branches
  - Method returns

Time to Safepoint (TTSP):
  Hidden GC pause component
  GC can't start until ALL threads reach a safepoint
  Long TTSP → long GC pause even if GC work is fast

Causes of long TTSP:
  - JIT-optimized loops without safepoint polls
  - Slow JNI calls
  - Threads deep in blocking I/O

  Profilers sampling only at safepoints see incorrect profiles

```

# Interview Preparation — Safepoints

---

## Q1: What is a safepoint in the JVM?

**Answer:**

A safepoint is a point in a thread's execution where its state is fully known and consistent — all object references are in known memory locations (not hidden in CPU registers), and the JVM can safely examine or modify the heap.

The JVM compiler inserts "safepoint polls" at method calls, backward loop branches, and method returns. When the JVM needs to stop threads (for GC, thread dump, deoptimization), it signals all threads. Each thread stops at its next safepoint poll.

Safepoints are the underlying mechanism for all Stop-The-World operations. Without them, GC cannot safely trace object references.

---

## Q2: What is Time to Safepoint and why does it matter for GC pauses?

**Answer:**

Time to Safepoint (TTSP) is the time between the JVM requesting a safepoint and all threads reaching one. It is a hidden component of GC pause time:

```text
Total GC pause = TTSP + actual GC work
```

If TTSP is 200ms and GC work is 10ms, the observed pause is 210ms — even though the GC itself was fast.

Common causes of high TTSP:
1. JIT-optimized tight loops that the JIT chose not to insert safepoint polls into
2. Slow JNI calls that must complete before reaching a safepoint
3. Many threads that all need to independently reach safepoints

Monitor with: `-Xlog:safepoint*` — look for high `spin` or `sync` times in the output.

---

## Q3: What is safepoint bias in profiling?

**Answer:**

Safepoint bias is a systematic inaccuracy in profilers that can only take stack samples at JVM safepoints.

Methods in tight loops (JIT-optimized, no safepoint polls) appear less often in samples than their actual CPU time warrants. Methods with many method calls (many safepoints) appear more often.

Result: the profiler shows an incorrect picture — you might think method B is the bottleneck (many samples) when method A is actually using more CPU.

`async-profiler` uses the Linux `AsyncGetCallTrace` mechanism (via SIGPROF signal) to sample at ANY point, not just safepoints — giving an unbiased, accurate CPU profile. This is why `async-profiler` is recommended over JVM's built-in sampling profiler.

---

## Q4: How do safepoints relate to Stop-The-World GC pauses?

**Answer:**

Every Stop-The-World GC pause requires a safepoint:

1. GC requests a global safepoint (makes polling pages inaccessible)
2. All threads hit their next safepoint poll → page fault → they pause
3. Each thread signals "I'm paused and safe"
4. GC waits until ALL threads are paused
5. GC does its work (mark, copy, compact)
6. GC releases the safepoint
7. All threads resume

The "wait for all threads" step is TTSP. Even concurrent GCs like G1 and ZGC need brief STW safepoints (for initial marking, remark). ZGC achieves sub-millisecond STW by minimizing what work requires safepoints and doing most work concurrently.
