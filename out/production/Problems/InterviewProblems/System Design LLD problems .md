# System Design & Low-Level Design Interview Questions (Sorted by Difficulty)

This roadmap outlines common **low-level design (LLD)** and system-design problems from basic to advanced. Each question includes a typical interview prompt (with scope and constraints) and links to quality solutions or explanations. The questions are grouped by difficulty (and theme/pattern) to help you build skills step-by-step.

## Easy – Core Data Structure & Simple OOD Problems

- **LRU Cache (Data-structure design)** – *“Design and implement a data structure for a Least Recently Used (LRU) cache.”* The cache should support `get(key)` and `put(key,value)` in **O(1)** time. On `put`, if capacity is exceeded, evict the least-recently-used entry.  
  *Example constraints:* fixed capacity `N` (e.g. 10³), key/value ranges, up to ~10⁵ ops.  
  *Key patterns:* Use a hash map + doubly-linked list for O(1) access and recency ordering.  
  *Solutions:* Standard problem (LeetCode 146) – see descriptions on LeetCode/GeeksforGeeks and this [Hello Interview guide](https://www.hellointerview.com) covering the API and constraints.  

- **Parking Lot System (OOD)** – *“Design a parking lot system with multiple floors.”* For example, each parking spot is of type 2-wheeler or 4-wheeler, and the lot has multiple identical floors (each with R rows × C columns of spots). Implement methods like `init(floors, layout)`, `park(vehicleType, vehicleNo, ticketId, strategy)` and `removeVehicle(spotId)`. Two parking strategies may be supported: (0) **“first-available”** (lowest floor/row/column free spot) or (1) **“max-free-floor”** (choose floor with most free spots). Also support `searchVehicle(query)` (find by vehicle number or ticket) and `getFreeSpotsCount(floor, type)`.  
  *Example scope:* Spot types: 2-wheel or 4-wheel (0 = inactive, 2 or 4 in input array). Spot IDs are `"floor-row-col"`. Assume up to 5 floors and 10⁴×10⁴ spots per floor.  
  *Key patterns:* Class hierarchy for `ParkingLot`, `Floor`, `ParkingSpot`, `Ticket`, `Vehicle`, etc.; **Singleton** for parking lot instance; **Factory/Strategy** for spot allocation logic.  
  *Problems like this appear at Amazon/Microsoft/Uber/etc.. For a solution example, see GeeksforGeeks [“Designing a Parking Lot using OOP”](https://www.geeksforgeeks.org/system-design/design-parking-lot-using-object-oriented-principles/) or similar LLD tutorials.

- **Vending Machine (Stateful OOD)** – *“Design a vending machine that dispenses items and returns change.”* Requirements typically include: display available items/prices, accept coins/bills, dispense selected items, return change, and handle edge cases (insufficient funds, out-of-stock). The machine should be extensible to new products or payment types.  
  *Example features:* Support inventory of products (e.g. `{"Soda":1.25, "Chips":0.99}`), accept denominations (e.g. 1,5,10,25 cents), compute and dispense change, cancel transactions.  
  *Key patterns:* **State** pattern to manage states (Idle, ItemSelected, PaymentInProgress, Dispensing) and **Strategy/Factory** for payment methods; **Singleton** for the machine instance.  
  *Problem statement:* “Design a vending machine that (a) displays items/prices; (b) accepts coins/notes; (c) dispenses items; (d) returns change; (e) handles insufficient funds or out-of-stock; (f) allows easy addition of new products/payment types.” See the walkthrough in this Medium article for a detailed design.

- **Library Management System (Catalog & Borrowing, LLD)** – *“Design an in-memory library management system.”* Essential operations include: add books, register/unregister users, borrow (`requestBorrow`) and return books, and handle reservations with waitlists. For example, if all copies of a book are checked out, new borrowers join a FIFO waitlist. The system also tracks fines (e.g. ₹20 per day overdue beyond 14 days) and enforces rules (a user may not borrow multiple copies of the same book).  
  *Example requirements:* Each book has a unique `bookId`, title, author, and copy count. Users identified by `userId`. Methods include `addBook(title,author,copies)`, `registerUser(userId,name)`, `requestBorrow(userId, bookId, day)`, `returnBook(userId, bookId, day)`, etc.  
  *Key patterns:* Classes for `Book`, `User`, `Library` (controller). Use maps/queues to track copies, issued books, and waitlists (per-book FIFO queue).  
  *Problem statement:* “Design and implement an in-memory library system: supports adding books to catalog, registering users, borrowing books by ID (with a FIFO waitlist when unavailable), returning books, and calculating late fines.” For full details and example methods (including book-ID generation rules and fine logic), see the CodeZym practice problem description.

## Medium – Concurrency & Service Patterns

- **Meeting Room Reservation (Scheduling)** – *“Design a meeting room booking system.”* You have a fixed set of conference rooms. Implement operations to book and cancel meetings by time range, ensuring no two meetings overlap in the same room. If multiple rooms are available for a requested time, assign the one with the lexicographically smallest ID.  
  *Example specification:* Class `RoomBooking` with constructor `RoomBooking(List<String> roomIds)`. Methods: `String bookMeeting(meetingId, startTime, endTime)` returns a room ID or `""` if none available; `boolean cancelMeeting(meetingId)`. Time ranges are inclusive (an ending at `t` conflicts with one starting at `t`). Return lexicographically first room for ties. Example: booking, cancellation and search by time, up to ~10⁵ operations.  
  *Key patterns:* Interval scheduling and search (e.g. each room tracks its booked intervals). Use sorted maps or trees per room, and a global map from meetingId→room.  
  *Problem statement:* From an Uber interview – “Design a simple meeting room reservation system. Given fixed `roomIds`, support `bookMeeting(meetingId, start, end)` (returning an available room or `""`) and `cancelMeeting(meetingId)`. Ensure no overlapping meetings in a room, use FIFO tie-break (lexicographically smallest room).” See the full prompt (with examples and constraints) here.

- **Rate Limiter (Algorithmic OOD)** – *“Design a rate-limiting system.”* The system restricts API requests per user within a time window. It should support configurable limits and algorithms (fixed window counter, sliding window, token bucket, etc.). On each request, either allow or reject based on the user’s current usage.  
  *Example requirement:* For each user, specify `maxRequests` per `timeWindow`. The system must check each request and return allow/reject. It should be extensible to add new algorithms.  
  *Key patterns:* **Strategy** pattern for interchangeable algorithms (e.g. Counter, Sliding-Window, TokenBucket classes implementing a common interface), and a **Factory** or registry to create them. Concurrency considerations: updates must be thread-safe (counters or timestamps in concurrent maps).  
  *Problem statement:* “Design a rate-limiting system that restricts the number of API requests a user can make within a given time window. Support multiple rate-limiting algorithms (e.g. fixed window, sliding window, token/leaky bucket) that can be configured or extended.” See this LLD discussion for details on requirements and examples.

- **Restaurant Food Ordering System** – *“Design a food ordering and rating system (like Swiggy/Zomato).”* Manage restaurants, food items, orders, and ratings. Users can place orders for single-item orders (simplified), then rate their orders. The system should fetch top-rated restaurants overall and top restaurants for a specific food item.  
  *Example requirements:* Initialize `init()`. Methods: `orderFood(orderId, restaurantId, foodItemId)`, and `rateOrder(orderId, rating)` (1–5 stars). Ratings apply to both the restaurant overall and that specific food item. Queries: `getTopRestaurantsByFood(foodItemId)` and `getTopRatedRestaurants()` return lists of top-20 restaurant IDs by average rating (ties broken lexicographically). Up to 50 food items, 10⁴ restaurants, each with ≤25 items.  
  *Key patterns:* Maintain data structures (maps and heaps or sorted lists) tracking each restaurant’s overall rating and per-item rating averages. Update averages on `rateOrder`.  
  *Problem statement:* “Design a restaurant ordering and rating system like Swiggy. The system has food items and restaurants (a food item can be sold by many restaurants). Users can `orderFood` (single-item order) and then `rateOrder`. Implement queries to get the top-20 restaurants by overall rating and by rating **for a particular food item**. Unrated restaurants appear lower, and ties use lexicographic order.” The CodeZym prompt above provides the complete spec.

## Hard – Complex Systems & Advanced OOD

- **Elevator Management System (Multiple Lifts)** – *“Design an elevator (lift) control system for a multi-story building.”* The building has `F` floors and `L` lifts (numbered 0..L-1), each with the same capacity. Implement methods to initialize the system and to handle lift requests. For example:  
  - `init(floors, lifts, capacity)`: set up the system.  
  - `int requestLift(int startFloor, char direction)`: called when a user on `startFloor` presses 'U' or 'D'. Return the index of the **eligible** lift that can serve this request in minimum time, or -1 if none. (“Eligible” means the lift has not already passed the start floor in the requested direction and won’t drastically delay current passengers; choose the most optimal lift otherwise, breaking ties by smallest index.)  
  - `void pressFloorButtonInLift(int liftIndex, int floor)`: a passenger inside a lift presses the destination floor button.  
  - You may also support a time-advance `tick()` method (each call simulates 1 second, moving each active lift by one floor).  
  *Key patterns:* Model each `Lift` with its state (current floor, direction, destination queue). Use scheduling logic to assign requests according to rules (as in standard elevator control algorithms). Example rules given by a Microsoft interview include disqualifying lifts that have “passed” the call or are serving opposite directions.  
  *Problem statement:* From a multi-company LLD round: “Design a simple elevator system with multiple lifts in one building. Lifts are numbered 0..L−1, floors 0..F−1. Implement methods: `requestLift(startFloor, direction)` – choose an eligible lift (minimize travel time, break ties by index) or return -1. (An elevator is *ineligible* if it has already passed the requester in that direction or is committed to opposite requests.) [Detailed cases follow as examples】.” The CodeZym prompt above includes the full method signatures and eligibility rules.

- **Chess Game (Game Simulation)** – *“Design a game of chess using object-oriented principles.”* Implement the classes and rules of chess. The board is 8×8, each cell can hold one piece or be empty. There are 6 piece types (King, Queen, Rook, Bishop, Knight, Pawn) and two players (White vs Black). Each piece has its movement rules. Implement turns, piece placement, moves (including captures), and end-of-game detection.  
  *Example requirements:* Define classes like `Board`, `Spot`, `Piece` (abstract) with subclasses `King`, `Queen`, `Rook`, etc., and a `Game` controller. Methods include initializing the board, making a move (`move(startX,startY,endX,endY)`), reporting invalid moves, and checking game status (e.g. `getNextTurn()`, `getGameStatus()`).  
  *Key patterns:* Class hierarchy with inheritance for pieces; **Factory** or enum for piece creation; careful encoding of move rules for each piece type. Use a `Game` class to track current turn and check for checkmate (often simplified to “king capture ends game”).  
  *Problem statement:* As asked at Microsoft/Adobe/etc.: “Write code for the low-level design of the chess game. We have an 8×8 board and 6 kinds of pieces: K (king), Q (queen), R (rook), B (bishop), H (knight/horse), and P (pawn), each colored white or black. Implement the movement rules (e.g. queen moves any distance orthogonally/diagonally, knight moves in ‘L’ shapes, pawn moves 1 forward or captures diagonally, etc., as listed above). A move is invalid if it ignores these rules or captures a friendly piece. Track turns (white moves first) and end the game when a king is captured.” For a detailed design, see this GfG article or tutorials on chess OOD.
